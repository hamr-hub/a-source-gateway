# 优化空间与可行性报告

> 评估对象:a-source-gateway **v1.1**(2026-10)
> 方法:以本仓库的实测基线为准,每条优化给出**当前证据 → 收益量化 → 实现代价 → 结论**。
> v1.0 的原始结论保留在 §3 里并标注了状态;v1.1 的双语言分层带来了新的成本项(§2.3)。

---

## 1. 现状基线(v1.1)

### 1.1 架构与规模

| 维度 | v1.0(Python 单体) | v1.1(双平面) |
|---|---|---|
| 网关运行时 | FastAPI + uvicorn | **Go**(stdlib,无第三方依赖) |
| 解析运行时 | 同进程 | **Python 子进程**(NDJSON over stdio) |
| 源码规模 | 2,688 行 / 10 模块 | Python ~4,300 行 + Go ~7,900 行 / 13 包 |
| 运行时依赖 | 4 个(fastapi/httpx/pydantic/uvicorn) | 同样 4 个 + **Go 侧 0 个** |
| 事实源 | CSV + JSON(2 份) | CSV×2 + JSON×2(**4 份**:海外清单/国内清单/端点定义/别名) |
| 源覆盖 | 97 源 / 109 端点 | **109 源 / 154 端点**(海外 107 + 国内已接入 2);另有 32 个国内候选待接入 |
| 注册表构建 | 运行时构建(6.4ms) | 运行时构建,**两个实现 + parity 校验** |
| 注册表体积 | 117 KiB | 同上 |
| 缓存上限 | 512 条 / 32 MB 双封顶 | 同上 |
| 上游取数墙钟 | 400 ms(总预算 500,预留 100) | 同上 |
| 正文上限 | 1 MB;CSV/TSV 最多 15000 行 | 同上 |

### 1.2 延迟基线

| 指标 | 实测 |
|---|---|
| 元数据 p95 | 4.7 ms |
| 热路径中位 | 1.6 ms |
| 热路径 p95 最差 | 405.5 ms(该值由冷路径样本混入) |
| 冷路径(强制 cache miss)最差 | 421.7 ms |
| 超预算用例 | **0** |
| 热路径有数据 | 11–12 / 12 |

### 1.3 已知的环境性波动

SEC 系源(`sec/submissions`、`sec/company_tickers`)在**连续高频访问**下会出现上游 403,
或后台补数尚未完成导致的降级态。隔离复测(单源、间隔访问)**完全正常**:
首次 401 ms 降级 → 后台补数约 1 s 完成 → 二次查询 0 ms 返回 `total=1002`。

**结论**:这是本机网络与上游限流的交互,不是网关逻辑缺陷。基准因此做了两处设计:
未配置 `A_GATEWAY_CONTACT` 时**跳过**需要邮箱 UA 的源;热路径阶段**主动等到缓存真的热了**再测。

### 1.4 元数据完整度

| 维度 | 覆盖 |
|---|---|
| 源级字段(认证/限速/规模/增量/代理策略/风险/别名) | 109 / 109 |
| 端点级请求描述(method/url/headers/params) | 154 / 154 |
| 端点级响应描述(shape/media_type) | 154 / 154 |
| 端点级**字段级**响应结构(`response.fields`) | 46 / 56 专用端点来源(通用透传端点无字段可列) |
| `scale.total` 有确切数字 | 60 / 109(其余 49 个源没有公开计数端点,`basis` 写明了计数口径) |
| 官方链接可达性 | 86 × 200 / 5 个其他可达响应(202/302/307/405)/ 15 需凭据或浏览器 UA(401/403)/ 3 本机网络不可达 / **0 死链** |

## 2. v1.1 本轮已落地

### 2.1 双语言分层(ADR-015 ~ ADR-018)

| # | 优化 | 收益 | 代价 |
|---|---|---|---|
| 1 | **Go 网关面** | 网关侧并发/内存/硬 deadline 由 Go 承担;`context` 让"总墙钟"预算表达最直接;Go 侧零第三方依赖 | 与 Python 侧存在**两份注册表实现**,需 parity 守住 |
| 2 | **Python 解析面 + NDJSON 子进程** | 解析(内容密集)交给 Python;stdlib 足够,零新增依赖;stdout 协议专用便于调试 | 多一个进程;单条解析串行,靠多协程横向扩展 |
| 3 | **Go 内置 JSON 兜底解析**(`A_GATEWAY_PARSER=go`) | 没有 Python 也能跑;镜像可裁剪 | 与 Python 侧重复一份 JSON 投影实现 |
| 4 | **别名表数据文件化**(`data/aliases.json`) | "加源不改代码"成为硬约束 —— 这是 AI 自助接入的前提 | 多一份数据文件;wheel force-include 多一行 |
| 5 | **注册表 parity 校验** | 两套派生规则(认证分类/规模解析/slug)漂移会在 CI 里亮红灯 | CI 多一个 job;改一处必须改两处 |

### 2.2 自助接入流水线(ADR-020)

| # | 优化 | 收益 | 代价 |
|---|---|---|---|
| 6 | **`scripts/recon.py`** | 侦察自动化:可达性/认证/限速头/推断的 `item_path`+`total_field`,每项带推断依据 | 启发式会误判 —— 所以推断可被人工纠正,且不构成最终结论 |
| 7 | **`scripts/scaffold_source.py`** | 生成 CSV 行 + 端点定义草稿 + `REPORT.md`(标注待补 TODO);默认**不动**真实数据文件 | 语义类字段(族/限速口径/规模口径)仍需人补 |
| 8 | **`scripts/verify_source.py`** | **证据关卡**:真实请求 + 断言(item_path 真是列表、total_field 真是数字、字段名真的出现)+ 真实样本;三态结论(通过/失败/不可达) | 需要真实网络;不可达时只能报"未验证" |
| 9 | **`scripts/demo.py`** | 交付物标准化:调用示例 + 真实数据 | 无 |
| 10 | **`AGENTS.md` + `CLAUDE.md`** | 智能体打开仓库就能按九步流程干活,不用读全仓库 | 需要随实现同步更新 |

### 2.3 双平面带来的新成本(需要持续投入)

| 成本项 | 量级 | 缓解手段 |
|---|---|---|
| **两份注册表实现** | 派生规则约 200 行 × 2 | `make parity` + CI job;改一侧必改另一侧 |
| **两份信封/指标定义** | 指标名约 12 个 × 2 | 指标名写进文档与契约;parity 顺带比对 |
| **跨语言 IPC 契约** | NDJSON 请求/响应各 1 个 schema | 契约写进 ADR-016;解析器有单元测试 |
| **端到端行为差异** | URL 渲染/投影/降级各有边界情形 | 以 Python `resolver.py` 为参照实现;Go 侧逐项对齐 |

> **实测结论**:跨进程 NDJSON 往返在热进程下约 1–3ms,相对 500ms 预算占比 <1%。
> 这是把解析放进 Python 的代价,也是目前**不合并回单语言**的依据(ADR-015 重评条件)。

## 3. 待优化空间(按优先级)

### P0 —— 影响正确性或可用性

#### 3.1 端点覆盖率:56 / 109 源有专用端点(101 条端点定义)  ⬜ 未做

**现状**:109 个源里只有 56 个有结构化端点定义,其余 53 个走通用透传端点(`entry`)——
能取到数据,但调用方拿不到参数说明与响应结构。

**收益**:每补一个源的端点定义,该源的调用方就能少猜一轮字段。实测里最费时间的就是
"字段藏在三层嵌套里"。

**代价**:每个端点约 20–40 行 JSON,人工核对上游文档 + 实测响应。**63 个源 ≈ 1.5–2 人日**。

**可行性**:**高**。纯数据工作,可众包;`endpoints.json` 的结构已经定型,照着填即可。
**v1.1 之后更好做了**:`scripts/recon.py` + `scaffold_source.py` 把"探测 + 生成"自动化了,
人只负责核对语义 —— 单源成本从 20–40 分钟降到约 10 分钟。

**建议**:按"族"分批,优先补调用最频繁的 20 个源。用脚本流水线做初稿,人核对。

#### 3.2 规模数字:60 / 109  ⬜ 未做

**现状**:46 个源没有公开的计数端点(FCA 注册处、各州注册局、专利局等)。

**收益**:有了数字才能做"这个源值不值得接"的判断。

**代价**:逐源查;部分需申请 key 或付费账号。

**可行性**:**中**。已知的部分可以补(Eurostat 目录、USPTO 批量文件行数),真正没有的
(各州注册处)只能写口径不写数字 —— 现在 `basis` 字段已经这样做了。

**建议**:不追求 100%。**诚实比完整重要**:`basis` 写清"用哪个端点的哪个字段计"即可。

#### 3.3 链接状态是 2026-10-22 的一次性快照  ✅ 部分解决

**现状**:`link_status` 列是当时测的,没人在维护。

**v1.1 已做**:`.github/workflows/link-check.yml` 定时复验官方入口,
**结果进 issue 而不是直接改主分支**(上游抖动很常见,自动改会把清单改脏)。
401/403 视为"可达但有门禁",不算失败。

**剩余**:复验结果的**结构化落库**还没有 —— 目前只在 issue 里。要长期跟踪某个源的
可用性趋势,需要把结果写进一个 `data/link_health.json` 之类的文件(由定时任务生成,
人审后合并)。**代价** 0.5 人日,**可行性** 中(要先定义"多久算坏")。

#### 3.4 上游响应契约测试  ⬜ 未做

**现状**:上游改了字段结构,网关不会立刻发现 —— 表现是"查到了但某些字段是 null"。

**收益**:把真实响应的形状固化成 JSON Schema,放进 CI 定期回归。

**代价**:需要定期打真实上游(放进带 `network` 标记的测试)。

**可行性**:**高**,且与 §3.3 的链接复验可以合并成同一个定时任务。
**v1.1 之后更容易**:`scripts/verify_source.py --json` 已经产出了结构化的验证报告,
把它接进定时任务即可拿到"响应结构是否变化"的信号。

#### 3.5 Go / Python 双实现的漂移面  ✅ 已缓解

**现状**:两份注册表实现、两份信封、两份指标定义。

**v1.1 已做**:`make parity` 校验两侧注册表一致,CI 里是独立 job;parity 失败即红灯。

**剩余**:parity 目前只比对注册表。**信封与指标名的一致性还没自动校验** ——
可以扩展 parity job:两边各导出一份"空信封"与"/metrics 快照",diff 之。
**代价** 0.5 人日,**可行性** 高。

### P1 —— 影响性能与弹性

#### 3.6 按端点自适应预算  ⬜ 未做

**现状**:所有端点统一 400 ms 上游墙钟。

**问题**:实测快源(ClinicalTrials 596 ms、World Bank 376 ms)与慢源(Eurostat 5.8 s)
差异巨大。慢源必然降级,快源却也占满了预算才降级。

**收益**:按端点历史 P95 分配预算(快源 150 ms / 慢源 400 ms)。好处有二:
① 快源的失败更快暴露;② 慢源省下的时间可以给同一请求里的其他源。

**代价**:需要收集端点级延迟样本(`/metrics` 的按源指标可作基础)。

**可行性**:**高**。`EndpointSpec.budget_ms` 字段已存在,只差一个"根据观测调整"的策略层。

#### 3.7 批量查询(一次请求多源)  ⬜ 未做

**现状**:一次 `/v1/query` 只能查一个源。

**收益**:典型场景是"查一个实体在多个源的状态"(LEI + 制裁 + 专利 + 财报)。
批量接口可以在**同一个 500 ms 预算内并发**发多个请求,而不是让调用方发 N 次。

**代价**:需要定义批量语义(部分失败怎么办?共用预算怎么分?)。

**可行性**:**高**。`resolver.query` 已经是 async,加一个 `query_many` 即可。
关键设计:批量场景下每个源的上游预算应该**按占比分配**,而不是各给 400 ms。

> **v1.1 备注**:Go 网关天生并发,批量查询在 Go 侧实现比 Python 侧更自然
> (goroutine + 共享预算上下文)。这是双平面的一个额外收益。

#### 3.8 游标透传  ⬜ 未做

**现状**:`next_cursor` 字段存在但恒为 `null`,`truncated=true` 时调用方拿不到下一页。

**收益**:OpenAlex / Crossref 这类游标分页的源,调用方目前只能拿到第一页。

**代价**:需要在上游 URL 里正确透传 cursor 游标参数 —— 这与"页大小归一"是同一类问题,
需要在 `EndpointSpec` 里声明"哪个参数是游标"。

**可行性**:**中**。需要改端点定义格式 + 缓存键要包含游标(否则不同页会互相覆盖)。

#### 3.9 跨进程共享缓存  ⬜ 未做

**现状**:缓存是进程内的。多 worker 部署时每个进程一份,命中率被摊薄。

**收益**:多实例部署下命中率显著提升。

**代价**:引入 Redis 依赖(违背"轻量、零依赖"的定位)。

**可行性**:**中**。建议做成**可选**:`A_GATEWAY_CACHE_BACKEND=redis` 时启用,默认仍是内存。
另一个零依赖方案是**只读预热**:由一个后台进程把热数据推到各实例的 HTTP 缓存接口。

### P2 —— 影响可观测与工程质量

#### 3.10 精确分位数  ⬜ 未做

**现状**:`/metrics` 只有 avg / max。

**收益**:P95/P99 是延迟 SLO 的标配。

**代价**:自己实现滑动窗口直方图(约 100 行),或把 `prometheus_client` 变成可选 extra。

**可行性**:**高**。建议后者 —— 一个可选依赖不违背轻量定位。

> **v1.1 备注**:Go 侧实现直方图成本更低(`prometheus/client_golang` 是标准选择),
> 但那会给 Go 侧引入第一个第三方依赖,与"只用标准库"的决定冲突。
> 建议 Go 侧也手写一个固定桶的滑动窗口(约 80 行),保持两侧都零依赖。

#### 3.11 OpenTelemetry 追踪  🟡 部分解决

**现状**:无分布式追踪。

**v1.1 已做**:信封里加了 `meta.trace_id`(零成本),调用方能自己串起来。

**剩余**:真正的跨进程 span 导出。

**可行性**:**中**。做成可选 extra;或维持现状。

#### 3.12 批量/并发下的限速公平性  ⬜ 未做

**现状**:限速是按站 token bucket。批量查询一旦落地,单次请求会并发打多个源 ——
每个源各按自己的额度限速是合理的,但**同一个源被多个并发请求同时打**时的排队策略
尚未定义。

**代价**:定义 FIFO / 优先级,并在指标里暴露排队时长。

**可行性**:**中**。必须与 §3.7 一起做,否则批量查询会在上游限速下把请求打挂。

### P3 —— 架构级选项

#### 3.13 边缘部署(Cloudflare Worker)  ⬜ 暂缓

**现状**:网关跑在中心机房。从国内访问欧美上游的延迟是主要瓶颈(实测 0.4–7.5 s)。

**收益**:把**元数据层**放到边缘,数据回源时按地理位置选路,可把冷路径延迟降低一个数量级。

**代价**:Worker 侧要用 `fetch` 重写取数层;Python 逻辑无法直接复用。

**可行性**:**中低**。推荐折中方案:**边缘 Worker 只做元数据缓存与请求路由**(纯 JS),
实际取数仍由区域化的 Go 网关承担 —— v1.1 之后,Go 网关比 Python 服务更适合做区域化部署
(单二进制、启动快、内存小)。

#### 3.14 HTTP/2  ⬜ 暂缓

**现状**:Go 的 `http.Transport` 默认尝试 HTTP/2;Python 侧 httpx 默认 HTTP/1.1。

**收益**:同 host 多请求可复用一条连接,对"批量查同一源"场景有效。

**代价**:部分官方站对 h2 支持不佳;Python 侧需要 `h2` 依赖。

**可行性**:**中**。收益与 §3.7(批量查询)重叠,建议等批量查询落地后再评估。

#### 3.15 源包市场(第三方贡献源定义)  ⬜ 设想

**现状**:源定义只能进主仓库的 `data/`。

**收益**:让"某个组织维护一批源"变成"提交一个源包",而不必改主仓库。

**代价**:需要定义源包 schema、签名、信任模型(第三方源定义是**可执行配置**的风险面)。

**可行性**:**低**。信任模型是主要难点 —— 建议在源数量与社区需求出现之前不做。

## 5. 不建议做的事(以及原因)

| 想法 | 为什么不做 |
|---|---|
| 内置代理池 / 多 IP 轮换 | 官方限速是**授权条件**。多 IP 绕过会触发 key 级风控,也会让审计链断裂。本项目立场明确反对。 |
| 把原始数据落库 | 109 个源的总量是 TB 级,且增量逻辑各不相同。落库会把"网关"变成"数据仓库",与本项目的定位相反。 |
| 内置爬虫 | 页面型抓取会撞各站条款与 robots。批量抓取是另一个工具的职责。 |
| 自研 HTTP 客户端 | Go 的 `net/http` 与 Python 的 httpx 都够用,自研只会带来 TLS/连接池/重定向的坑。 |
| 引入配置框架(pydantic-settings 等) | 十几个标量配置项用环境变量足够,多一个依赖不值。 |
| 把端点定义放回 Python/Go 代码 | 会让贡献者必须改代码才能加源,与开源目标背道而驰。 |
| 给 Go 侧引入第三方模块 | 目前 stdlib 完全够用;保持 `go build` 离线可用,减少供应链面。 |
| 让 AI 自动决定"这个源能不能接" | 合规判断必须由人给出理由(见 [`GOVERNANCE.md`](../GOVERNANCE.md) §4)。 |

## 6. v1.1 之后的新常态

**双平面不是免费的**,它换来的是:

- 网关侧的并发与硬预算表达力(Go);
- 解析侧的内容处理表达力与工具链迭代速度(Python);
- 代价是**两份实现要靠机器守住一致性**(parity in CI)。

因此 v1.1 之后的第一优先级不是加功能,而是**把漂移面收窄**:
parity 覆盖信封与指标、契约测试盯上游结构、脚本流水线让"加源"不再依赖手写代码。
这三件事做完,双平面才算真正站稳。
