# 技术选型

> 以 ADR(Architecture Decision Record)形式记录。每条包含:背景、候选、决策、代价、
> 什么条件下应该重新评估。

---

## ADR-001 网关运行时形态:HTTP API + MCP server 双形态

**背景**:目标用户有两类 —— 程序(要 REST)和 LLM/Agent(要 MCP 工具)。核心逻辑必须只有一份。

**候选**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只做 HTTP | 通用 | Agent 侧要自己包 MCP |
| 只做 MCP | Agent 友好 | 普通程序调用不便 |
| 两者共享 core | 各取所需 | 多一层抽象 |

**决策**:**两者共享 core**,`resolver.py` 是唯一实现;`api.py` 与 `mcp_server.py` 只是两种
传输适配层。core 不感知 HTTP/MCP。

**代价**:core 的返回类型必须设计成"传输无关"(用 dataclass 而非 dict 拼装)。

**重评条件**:若出现第二种传输需求(如 gRPC / WebSocket),core 无需改动。

## ADR-002 元数据格式:声明式数据文件,而非代码里的 Python 字面量

**背景**:v1.0 时的 97 个源、46 个端点定义。贡献者加一个源要不要改 Python?

**候选**

| 方案 | 优点 | 缺点 |
|---|---|---|
| Python 字典(初版) | 类型友好、能写逻辑 | 417 行字面量占 registry.py 的 46%;加源要碰代码 |
| YAML | 人友好 | 多一个依赖(PyYAML) |
| JSON | 零依赖 | 冗长,但机器友好 |
| TOML | 人友好 | 嵌套数组表达力弱,端点定义里有数组 |

**决策**:**端点定义用 JSON**(`data/endpoints.json`),**源清单用 CSV**(`data/source_inventory.csv`)。
两者都是零依赖、Git diff 友好、可以直接用表格工具审阅的纯数据。

**关键设计**:CSV 的每一列就是元数据的一个字段,列名即契约(见 `docs/adding-a-source.md`)。
加载时用 `csv.DictReader`,不做位置假设 —— 加列不会破坏旧行。

**代价**:失去了在定义里写动态逻辑的能力(比如按上游响应推导 URL)。判断为不值得。

**重评条件**:若端点定义需要复杂条件逻辑,应引入 JSON Schema 校验 + 少量 Python 钩子。

## ADR-003 注册表加载:运行时构建,而非打包预生成

**背景**:注册表约 120 KiB,构建耗时 6.4ms。

**候选**:预生成 `registry.json` 随包分发 / 运行时从 CSV+JSON 构建。

**决策**:**运行时构建**。

**理由**

1. 单一事实源:CSV 与 JSON 就是真相,预生成物必然存在"忘记重新生成"的漂移风险。
2. 贡献者只需改数据文件,不需要跑生成步骤。
3. 省掉一个 120 KiB 的生成物与一条 CI 流水线。

**代价**:每次进程启动多 6.4ms。对一个以网络往返(百毫秒级)为主的服务,占比 <0.01%。

**重评条件**:若源数增长到 1000+(构建耗时可能上百毫秒),改为**构建期生成 + 运行时可选加载**。

## ADR-004 HTTP 框架:FastAPI

**背景**:需要 OpenAPI 文档、请求体校验、异步、测试友好。

**候选**:FastAPI / Starlette 裸用 / Flask / Litestar / 标准库 `http.server`。

**决策**:**FastAPI**。

**理由**

1. 自动 OpenAPI —— 路由和 pydantic 模型直接产出文档。
2. pydantic v2 做请求体校验 —— `QueryRequest` 的字段约束(如 `limit ≤ 500`)直接生效。
3. `httpx.AsyncClient` 与 httpx 生态一致 —— 网关本身就用 httpx 抓上游,少一套 HTTP 栈。
4. 生态与人才面最广,开源友好。

**代价**:依赖树比裸标准库大(fastapi + pydantic + starlette)。

**已淘汰**:Flask 是同步的,与 `asyncio.timeout` 的预算模型不合;裸 Starlette 要自己写校验。

## ADR-005 上游客户端:httpx

**背景**:需要连接池、超时控制、流式读取(正文上限)。

**候选**:httpx / aiohttp / requests+ThreadPool / 原生 asyncio。

**决策**:**httpx**。

**理由**

1. 原生 async,API 与 `requests` 高度相似,迁移成本低。
2. 支持 `transport` 注入 —— 测试可以用 `MockTransport` 完全离线(见 `tests/test_resolver.py`)。
3. HTTP/2 支持成熟(可选)。

**代价**:默认用 certifi 证书包,部分官方站的证书链在系统信任库里才有效 ——
**必须显式传 `verify=ssl.create_default_context()`**,这是踩过的坑。

**注意**:httpx 的 `timeout` 是**每次 socket 操作**的超时,不是总时长。总时长必须用
`asyncio.timeout` 包裹。

## ADR-006 缓存策略:进程内有界 TTL + LRU

**背景**:数据不落盘,但要挡住重复查询。

**候选**:纯字典 / functools.lru_cache / cachetools / Redis / SQLite

**决策**:**自实现的有界缓存**(约 90 行):条目数上限 + 字节上限双保险 + TTL + 访问计数。

**理由**

1. 需要**同时**按条目数和字节数封顶 —— `lru_cache` 只有条目数,一条大响应就能吃光内存。
2. 需要**过期但可读**(用于 stale-while-revalidate 降级),标准 LRU 过期即删。
3. 需要访问计数(用于自适应 TTL:热条目短 TTL)。
4. 零依赖。

**代价**:跨进程不共享。多 worker 部署时每进程一份缓存 —— 已在优化报告里列为待办
(改 Redis 或加一层共享缓存)。

**重评条件**:部署形态变成多实例/多 worker 且缓存命中率成为瓶颈时。

## ADR-007 上游预算:总墙钟 deadline,而非每请求 timeout

**背景**:500ms 是对外承诺,必须严格成立。

**候选**

| 方案 | 行为 | 问题 |
|---|---|---|
| httpx `timeout=` | 每次 socket 操作 | 慢速持续吐数据时可远超预期 |
| httpx 客户端级 `Timeout(5.0)` | 每次 socket 操作 | **独立于预算**,会把 29MB 的响应掐断 |
| `asyncio.timeout()` | **总墙钟** | ✓ |

**决策**:`asyncio.timeout()` 包裹每次上游调用,客户端**不设** timeout。
预算拆分为:上游取数 ≤400ms + 解析/序列化预留 100ms。

**代价**:解析是同步 CPU 操作,`asyncio.timeout` 中断不了它 —— 所以额外加了
**解析护栏**(CSV 最多 15000 行、正文最多 2MB)。

**重评条件**:若实测发现解析耗时占比超 10%,考虑把 JSON 解析挪到线程池。

## ADR-008 上游页大小:网关归一,默认 25

**背景**:不同上游的"一页"大小差异巨大,直接透传 `limit` 会让缓存命中率崩掉。

**决策**:**网关统一按固定页大小向上游取**(`size`/`rows`/`per_page` 等参数归一到 25),
调用方的 `limit` 在网关侧切。字段特别肥的源(OpenAlex 单条约 25KB、Crossref 含
references 约 100KB)单独调小(`page_size` 字段)。

**理由**

1. 缓存键只由上游请求决定 —— 否则"要 3 条"和"要 50 条"是两个键,预热全部落空。
2. 正文体积可控 —— 避免响应超 2MB 上限被截断(截断会导致 JSON 解析失败,
   **看起来像"查到了但没数据"**)。

**代价**:调用方 `limit > 25` 时拿不到那么多条,需通过 `truncated` 标记告知。

## ADR-009 MCP 接入:官方 Python SDK

**背景**:需要 MCP 协议兼容。

**候选**:官方 `mcp` Python SDK / 自己实现 JSON-RPC over stdio / mcp-server-proxy

**决策**:**官方 SDK**,列为可选依赖(`[mcp]` extra),因为只跑 HTTP API 的人不需要它。

**理由**:协议细节(握手、能力协商、错误结构)自己实现成本高且易错。

**代价**:核心依赖多一个包;SDK 的低阶 `Server` API 相比高层 `FastMCP` 更啰嗦
(本项目用了低阶版,因为要精确控制工具描述与参数 schema)。

## ADR-010 元数据作为唯一事实源,原始数据不落库

**背景**:v1.0 时的 97 个源(现 109 个)的数据总量在 TB 级。

**决策**:**只存元数据**(源清单 + 端点定义,约 75 KiB 磁盘),原始数据按需取、不持久化。
缓存只保留"被查过的那几条",有界(512 条 / 32MB 双上限)。

**理由**

1. 绝大多数场景只需要"某个实体的最新状态",不需要全量。
2. 落库就意味着要处理增量、版本、删除 —— 而这些正是各源差异最大的部分。
3. 合规上更干净:不持有、再分发他人的数据副本。

**代价**:高频重复查同一批实体会反复打上游。缓存与 SWR 缓解了这一点。

## ADR-011 配置:全部走环境变量

**候选**:环境变量 / `.env` + 库 / YAML 配置文件 / pydantic-settings

**决策**:**环境变量**,`config.py` 里用 dataclass 集中声明与解析。

**理由**

1. 容器化部署的标准做法,无需额外依赖。
2. 12 因子:配置与代码分离。
3. 凭据(API key)天然走环境变量,不会误入版本库。

**代价**:复杂配置表达力弱(无嵌套、无列表)。当前配置项都是标量,可接受。

**重评条件**:若需要"多数据源配置文件"这类能力,应引入 YAML 配置并保留环境变量覆盖。

## ADR-012 TLS 校验:用系统信任库

**背景**:`treasury.gov` 等官方站在 httpx 默认的 certifi 包里验签失败(证书链不在 certifi 中)。

**决策**:`httpx.AsyncClient(verify=ssl.create_default_context())`,即**系统信任库优先**。
保留 `A_GATEWAY_VERIFY=none` 作为自有可信网络下的兜底开关,但**生产环境不要开**。

**理由**:系统库覆盖了企业代理、根证书等本地信任链,比任何单一 CA bundle 都更贴合实际。

**代价**:系统信任库可能比 certifi 宽松(受本机安装的根证书影响)。

## ADR-013 错误模型:信封内降级,而非 HTTP 错误码

**背景**:上游超时/404/403 是**正常业务状态**,不是网关故障。

**候选**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 失败时返回 5xx | 语义直白 | 调用方要区分"网关坏了"和"上游拒绝";Agent 侧难处理 |
| 失败时返回 200 + `meta.degraded` | 信封形状恒定,Agent 好处理 | 需要调用方看 `meta` |

**决策**:**200 + `meta.degraded=true` + `meta.errors[]`**。只有"请求本身不合法"
(未知源、未知端点)才返回 4xx。

**理由**

1. 信封形状恒定 —— 调用方只需写一套解析逻辑。
2. 对 LLM 友好:`meta.fallback.hint` 直接告诉它"接下来该干什么"。
3. 降级也是**有效信息**:调用方知道该直连上游。

**代价**:不看 `meta` 的调用方会误以为"查到了但没数据"。缓解:信封里 `degraded` 与
`errors` 始终存在,文档明确标注。

## ADR-014 可观测性:零依赖的 Prometheus 文本格式

**背景**:延迟、命中率、降级率需要可观测。

**候选**:prometheus_client 库 / OpenTelemetry / 结构化日志 / 零依赖手写

**决策**:**先零依赖手写 `/metrics`**(Prometheus 文本格式),日志用标准库 `logging`。
**不引入** prometheus_client 与 OpenTelemetry 作为运行时依赖。

**理由**

1. 指标种类少(约 10 个),手写成本低。
2. 少两个重量级依赖,对"轻量网关"的定位更匹配。
3. 需要分布式追踪时再引入 OTel —— 届时它是可选 extra,不影响现有用户。

**代价**:没有直方图(只有 avg/max),无法算精确分位数。

**重评条件**:需要 P95/P99 精确分位时,自己加滑动窗口直方图,或把 `prometheus_client`
改为可选 extra。

# 第二部分:双语言分层(v1.1)

> 上面 14 条是 v1.0(Python 单体)的决策,全部仍然有效。
> 下面 7 条是 v1.1 引入 Go 网关 + Python 解析面后的新决策。

## ADR-015 双语言分层:Go 网关 + Python 解析面

**背景**:项目目标明确"python 做解析,go 做 gateway"。v1.0 全部是 Python(FastAPI + httpx,
2,688 行):**网关职责**(路由/缓存/限速/预算/降级)与**解析职责**(识别响应结构)混在同一进程、
同一种语言里。

**候选**

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全 Python(v1.0 现状) | 一份实现,无跨语言契约 | 网关侧的并发/内存/冷启动受 Python 制约;与既定技术方向不符 |
| 全 Go | 单一运行时,部署最简 | 解析侧要重写 XML/CSV/TSV;丢掉 Python 生态 |
| **Go 网关 + Python 解析面** | 各用其长;契约显式可测 | 两套实现需保持行为一致;多一个进程 |

**决策**:**Go 网关 + Python 解析面**。

- **Go 拥有**:HTTP 路由、注册表、缓存(SWR + 自适应 TTL)、按站限速、总墙钟预算、
  上游取数与正文上限、指标。
- **Python 拥有**:响应解析与投影(JSON/XML/CSV/TSV/JSONL)、源级特殊逻辑、MCP 适配、
  贡献者工作流(CLI / 校验 / 接入工具链)。

**关键设计**:两者读**同一份** `data/` 文件 —— 不存在"两份元数据"。

**代价**:

1. 需要一份跨语言契约(见 ADR-016);
2. 同一套派生规则(认证分类、规模解析、slug)要在两种语言各实现一次,靠 parity 测试守住
   (见 ADR-017);
3. 部署要同时带两个运行时(见 ADR-021)。

**重评条件**:若解析面因 IPC 开销吃掉可观预算(实测应 <2%),或 Python 侧无法独立发布,
则合并回单语言实现。

## ADR-016 解析面通信:常驻子进程 + NDJSON over stdio

**背景**:Go 网关需要调用 Python 做解析。通信方式直接决定延迟、故障隔离与部署复杂度。

**候选**

| 方案 | 延迟 | 故障隔离 | 部署复杂度 |
|---|---|---|---|
| 每请求起一个 Python 子进程 | 高(解释器启动 ~80ms) | 好 | 简单 |
| **常驻子进程 + NDJSON over stdio** | **~1–3ms** | **好(崩了能重启)** | **简单,无端口** |
| 常驻子进程 + HTTP over unix socket | ~1–3ms | 好 | 需管 socket 生命周期 |
| gRPC / protobuf | 中 | 中 | 需生成代码,增依赖 |

**决策**:**常驻子进程 + 换行分隔 JSON(NDJSON)over stdin/stdout**。

**理由**:

1. 无端口、无 socket 权限问题 —— 容器里不用额外暴露端口,也不用配 service mesh。
2. 生命周期与 Go 网关绑定:网关退出它自然结束;它崩了网关能拉起新的。
3. 协议可读可测:一行一个 JSON,`echo` 就能手工调试。
4. Python 侧**零新增依赖**,只用标准库。

**关键设计**:stdout 是**协议专用**,日志一律走 stderr;每个请求必须产生且只产生**一行**响应,
否则会串协议。未知 op 返回错误行但**不退出**。

**代价**:单条解析请求串行处理(同一时刻一条);靠 Go 侧多协程 + 连接池横向扩展。

**重评条件**:若解析成为热点,改为多 worker 池(一进程多子进程,按 req id 路由)。

## ADR-017 单一事实源 + 双实现 parity 校验

**背景**:注册表由 `data/source_inventory.csv` + `data/endpoints.json` + `data/aliases.json`
三份声明式文件构建。ADR-003 选择运行时构建,就是为了避免"生成物与源文件不同步"。现在 Go 与
Python 都需要这份注册表。

**候选**

| 方案 | 优点 | 缺点 |
|---|---|---|
| Python 构建好 JSON,Go 只读 | 只有一份实现 | 引入构建期步骤(回到 ADR-003 放弃的形态);Go 启动依赖 Python |
| **两边各实现一份 + parity 测试** | **无构建期依赖,启动快** | **需维护 parity 机制** |
| Go 调用 Python 取注册表 | 一份实现 | 网关启动依赖 Python 进程;违背"Go 做网关" |

**决策**:**两边各实现一份,CI 里做 parity 校验**。

**理由**:注册表构建是纯计算(6ms 级),不值得为它引入跨进程依赖或构建期产物。真正危险的不是
"两处代码",而是"两处代码悄悄不一致"。**parity 测试把这种风险变成 CI 里的一盏红灯**,这比
消除重复更可靠。

**parity 校验范围**:源 id、源名、族、认证分类、规模数字、端点 id、`item_path`、`total_field`;
忽略 `generated_at` 这类易变字段。

**代价**:CI 多一个 job;派生规则变更必须同时改两处(改一处会被 parity 挡住)。

**重评条件**:若派生规则继续膨胀(需要复杂自然语言抽取),改为 Python 构建 + Go 只读 JSON。

## ADR-018 解析引擎选择:`auto` / `python` / `go`

**背景**:Python 解析面是主路径,但它是**独立进程** —— 可能因为镜像裁剪、依赖缺失、启动失败
而不存在。

**决策**:`A_GATEWAY_PARSER=auto|python|go`(默认 `auto`)。

- `auto`:启动时 `ping` Python worker;成功则用它,失败则回落 Go 内置 JSON 解析器并打**警告日志**。
- `python`:只用 Python worker;不可用时查询降级(**不静默换引擎**)。
- `go`:只用 Go 内置解析器(单进程部署,不需要 Python)。

**理由**:容错不该以"静默换引擎"的形式发生。`meta.parser` 字段**始终暴露实际使用的引擎**
(`python` / `go`),调用方与运维都看得见。

**代价**:Go 侧要维护一份 JSON 解析/投影实现,与 Python 侧重复(由 ADR-017 的 parity 思路覆盖)。

**重评条件**:若 Go 兜底实现与 Python 行为出现分歧且难以收敛,去掉 `go` 模式,只保留 `python`。

## ADR-019 别名表数据文件化

**背景**:别名表(源名 → 常用简称)原本是 `src/registry.py` 里硬编码的 `ALIASES` 字典(68 组)。
这与"加源不改代码"**直接冲突** —— 而"加源不改代码"是 AI 自助接入(ADR-020)的前提:智能体
不应该为了加一个源去改 Python 代码。

**决策**:迁到 `data/aliases.json`,Python 与 Go 都从数据文件读。

**理由**:

1. 别名是**元数据**,不是逻辑 —— 它本来就不该在代码里。
2. 它让"加一个源"真正变成纯数据操作。
3. 别名是**跨源唯一性**的高风险项(两个源抢同一个别名会导致解析歧义)。放进数据文件后
   可以用 `validate` 统一校验。

**代价**:数据文件多一份;`pyproject.toml` 的 wheel force-include 要加一行。

## ADR-020 智能体自助接入流水线

**背景**:项目要支撑这样的场景 —— "未来有新的网站,只 MCode 或 Claude 打开本项目,对它说
'把 xxx 网站加进来',就能自动分析目标网站数据、把代码改好、更新部署,最后给出调用示例和真实数据"。

**决策**:把接入流程固化成**脚本化流水线 + 仓库级操作手册 + 不可绕过的证据关卡**:

| 阶段 | 工具 | 产出 | 谁做 |
|---|---|---|---|
| 侦察 | `scripts/recon.py` | `recon.json`:状态码/认证/限速头/推断的 `item_path`+`total_field`(每项带推断依据) | 脚本 |
| 语义补齐 | — | 族/机构/限速口径/规模口径/增量策略 | **智能体判断** |
| 生成草稿 | `scripts/scaffold_source.py` | CSV 行 + endpoints 条目 + `REPORT.md`(标注待补 TODO) | 脚本 |
| 校验 | `make validate` | 通过 / 失败 | 脚本 |
| **证据关卡** | `scripts/verify_source.py` | 真实请求 + 断言 + 真实响应样本 | 脚本 |
| 部署 | `make up` | 新镜像 | 脚本 |
| **交付** | `scripts/demo.py` | 调用示例 + 真实数据 | 脚本 |
| 约束 | `AGENTS.md` | 三条硬规则 + DoD 清单 | 文档 |

**关键设计**:

1. **证据关卡不可绕过**:降级的调用**不算**验证通过;"连不上上游"(退出码 2)与"源有问题"
   (退出码 1)是两个**不同的结论**,不能混为一谈。
2. **不许编造**:侦察推断的每个字段都带 `inference`;无法确定的字段是 `null` + `warnings`,
   而不是猜一个值充数。
3. **人工判断不自动化**:限速口径、规模计数口径、增量策略、族归属由智能体/维护者补,
   脚本只标 TODO —— 这些是**合规与语义判断**,不是技术问题。
4. **只改数据文件**:加源不碰 `src/`(见 ADR-019)。

**代价**:多一套脚本(约 600 行)要维护;启发式推断会有误判 —— 所以推断必须可被第 2、6 步纠正。

**重评条件**:若误判率长期偏高,把启发式推断降级为"仅提示",全部要求显式声明。

## ADR-021 部署形态:单容器双进程

**背景**:Go 网关 + Python 解析面意味着运行时需要 Go 二进制与 Python 环境。

**决策**:单个容器镜像同时包含两者,**Go 网关是入口进程**,由它拉起并托管 Python 解析子进程
(ADR-016)。

**理由**:

1. 一个镜像 = 一套版本 = 不会出现"网关和解析面版本不匹配"。
2. 解析子进程的生死与网关绑定,不需要 systemd + supervisor 两层。
3. `A_GATEWAY_PARSER=go` 时 Python 甚至不被使用(但仍在镜像里,便于随时切换)。

**代价**:镜像更大(Go 二进制约 10–20MB + Python 运行时约 50MB);Python 运行时可选却仍占体积。

**重评条件**:若绝大多数部署只用 `go` 模式,拆出 `gateway`(无 Python)与 `gateway-full` 两个 tag。
