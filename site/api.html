API 参考

网关一共 13 条路由，全部返回 JSON。查数据的三条路由 （GET/POST /v1/query、GET /v1/sources）返回统一的 {meta, data, fields} 三段式信封；其余是元数据与运维接口。 单次调用的硬上限是 500ms，取不到就降级返回，不会挂死你。

i本文所有示例都用本机默认地址

基准地址是 http://127.0.0.1:8848（由 A_GATEWAY_HOST / A_GATEWAY_PORT 决定）。部署到别处时把它换成你的地址即可，其余不用改。

30 秒上手

先查一次源清单，再查一次数据：

bash
# 1. 有哪些源可查
curl -s http://127.0.0.1:8848/v1/sources?limit=3

# 2. 看一个源的端点参数与响应结构
curl -s http://127.0.0.1:8848/v1/sources/gleif_lei/endpoints/lei_records

# 3. 查数据(推荐 POST)
curl -s -X POST http://127.0.0.1:8848/v1/query \
  -H 'Content-Type: application/json' \
  -d '{"source":"gleif_lei","endpoint":"lei_records","params":{"size":2},"limit":2}'
✓第一次调用大概率是降级的

跨境源的上游往返实测 0.4–7.5s，而网关给上游的墙钟预算只有 400ms。 所以第一次调用通常返回 200 + meta.degraded=true + meta.fallback.upstream_url， 并在后台补数；几秒后调同一个查询就会命中缓存。这是设计行为，详见 信封与降级。

接口详解

GET / —— 服务概览

不查任何上游，纯本地生成。适合当作健康检查与路由清单。

字段类型含义
servicestring服务名，恒为 A-Class Source Gateway
versionstring服务版本，恒为 1.0（与信封里的 schema_version 不是一回事）
purposestring一句话说明网关做什么
budget_msint单次调用硬预算，恒为 500
sourcesint注册表里的源数量
familiesstring[]分类列表（按名称排序）
offlinebool是否离线模式
routesstring[]网关自述的业务路由表（7 条）
mcpobjectcommand 启动命令 + tools 五个 MCP 工具名
bash
curl -s http://127.0.0.1:8848/

GET /healthz —— 健康探针

响应体固定三个字段：{"ok":true,"sources":N,"offline":bool}。

bash
curl -s http://127.0.0.1:8848/healthz
{"ok":true,"sources":117,"offline":false}

GET /livez —— 存活探针

只说明进程活着，{"ok":true,"uptime_s":x}。uptime_s 保留一位小数。

bash
curl -s http://127.0.0.1:8848/livez
{"ok":true,"uptime_s":580.4}

GET /readyz —— 就绪探针

{"ok":bool,"sources":N,"offline":bool}。注册表为空（sources == 0）时 返回 503 且 ok=false；否则 200。 K8s 的 readinessProbe 用它，livenessProbe 用 /livez。

bash
curl -s -i http://127.0.0.1:8848/readyz | head -1
HTTP/1.1 200 OK

GET /metrics —— Prometheus 指标

Content-Type: text/plain; charset=utf-8，Prometheus 文本格式。 可直接被 Prometheus 抓取；不是 JSON。

bash
curl -s http://127.0.0.1:8848/metrics | head -20

GET /v1/schema —— 网关自身的 meta 规范

返回一份 JSON 规范，描述四个层级的字段：source_spec（一个数据源）、 endpoint_spec（一个可调用端点）、request（查询请求体）、 response_envelope（响应信封）。想知道"某个字段是什么意思"时先查它。

bash
curl -s http://127.0.0.1:8848/v1/schema | python3 -m json.tool

GET /openapi.json —— OpenAPI 3.1 描述

这份描述由 gateway/internal/server/openapi.go 手工维护，与路由表不是同一个事实源， 改路由时记得同步它。客户端生成器（openapi-generator、httpx 等）可以直接吃它。

bash
curl -s http://127.0.0.1:8848/openapi.json | python3 -m json.tool | head -40

字段含义

GET /v1/query —— 查询（浏览器友好）

和 POST 完全等价，只是把参数放到 URL 上，方便直接在浏览器里打开、或做成可分享的链接。 params 是一个 JSON 串，fields 是逗号分隔的字符串。

参数必填默认说明
source是—源 id（也接受别名，见下文）
endpoint是—端点 id
params否{}JSON 串，必须是对象；非法 JSON 返回 400
fields否空逗号分隔，只回这些字段
limit否20最多返回多少条，取值 1–500
since否空增量窗口起点（ISO 日期）
timeout_ms否500本次总预算，取值 50–500
console
$ curl -s "http://127.0.0.1:8848/v1/query?source=gleif_lei&endpoint=lei_records&params=%7B%22size%22%3A2%7D&limit=2"

$ curl -s "http://127.0.0.1:8848/v1/query?source=gleif_lei&endpoint=lei_records&params=notjson"
{"detail":"params 必须是合法 JSON"}

GET 方式少了 X-Gateway-Trace-Id 的自定义能力？不，GET 一样支持这个请求头。 GET 和 POST 唯一的差别就是参数放在哪。

POST /v1/query —— 查询（推荐）

请求体是一个 JSON 对象：

字段类型必填默认说明
sourcestring是—源 id
endpointstring是—端点 id
paramsobject否{}端点请求参数
fieldsstring[]否[]只回这些字段；必须是字符串数组
limitint否20最多返回多少条，取值 1–500
sincestring否""增量窗口起点（ISO 日期）
timeout_msint否500本次总预算，取值 50–500

任何一项不合法都返回 422，响应体是 FastAPI 风格的 {"detail":[{"type":...,"loc":[...],"msg":...,"input":...}]}：

console
$ curl -s -X POST http://127.0.0.1:8848/v1/query \
    -H 'Content-Type: application/json' \
    -d '{"source":"gleif_lei","limit":900}'
{"detail":[{"type":"missing","loc":["body","endpoint"],"msg":"Field required","input":null}]}

$ curl -s -X POST http://127.0.0.1:8848/v1/query \
    -H 'Content-Type: application/json' \
    -d '{"source":"gleif_lei","endpoint":"lei_records","limit":900}'
{"detail":[{"type":"less_than_equal","loc":["body","limit"],"msg":"Input should be less than or equal to 500","input":900}]}

未知 source 返回 404： {"detail":"未知数据源 xxx"}。但未知 endpoint（源是已知的情况下） 返回的是 200 信封，错误写在 meta.errors[].type = "endpoint_not_found" 里。

查询参数详解

source：源怎么解析

source 不一定非要写规范 id。网关按这个顺序匹配： 精确 id → 别名 → 规范化 id（小写、去非字母数字）→ 规范化名称 → 唯一子串命中。 子串命中多于一个时，取名称最短的那个。纯中文的 key 匹配不上（规范化后为空）。

bash
# 三种写法都能命中同一个源
curl -s "http://127.0.0.1:8848/v1/sources/gleif_lei"
curl -s "http://127.0.0.1:8848/v1/sources/gleif"
curl -s "http://127.0.0.1:8848/v1/sources/GLEIF%20LEI"

params：端点参数

params 里的键必须对上端点定义里的参数名。先用 GET /v1/sources/{id}/endpoints/{eid} 查参数表：required=true 的参数缺了不会在请求层报错，而是返回一个 200 信封 + meta.errors[].type = "missing_param"。

没有被端点模板用到的参数会被追加成 query string；空值会被丢掉； 所有占位符的值都做 percent 编码（path 参数保留斜杠），所以调用方不能通过参数 注入 & 或 #。

fields：只回需要的字段

fields 是顶层字段名白名单，对每条记录生效。投影由网关在解析后完成， 不改变上游请求，所以带不带 fields 命中的是同一个缓存条目。

bash
curl -s -X POST http://127.0.0.1:8848/v1/query \
  -H 'Content-Type: application/json' \
  -d '{"source":"gleif_lei","endpoint":"lei_records","params":{"size":2},"fields":["type","id"],"limit":2}'

limit：截断规则

  • 默认 20，范围 1–500，越界 422。
  • 命中缓存时，limit 只切缓存里的结果，不重新取上游。
  • 上游页大小由端点定义决定；size / rows / per_page 这类参数会被统一成同一个有效值，避免"3 条"和"50 条"打到两个缓存键上。

since：增量窗口起点

传一个 ISO 日期字符串。网关把它原样接收，但当前不用它裁剪结果； 每个源的增量口径（频率、日增量、怎么取）写在源元数据的 increment 字段里， 请以那份口径为准。

timeout_ms：本次预算

默认 500，范围 50–500，越界 422。 它是整个请求的总预算（上游 + 解析 + 序列化），不是给上游单独留的时间。 调小它会让网关更早放弃并降级；调大也不行，超过 500 会被钳住。 详见 预算与延迟。

状态码

码什么时候响应体
200 正常返回，包括降级：降级是 200 + meta.degraded=true，不是 5xx 查询接口给 {meta,data,fields}；其他接口给各自的形状
400 只有 GET /v1/query：params 不是合法 JSON，或不是 JSON 对象 {"detail":"params 必须是合法 JSON"}
404 未知源 / 未知端点（描述类接口）/ 未知路径 {"detail":"未知数据源 xxx"}、{"detail":"未知源 xxx"}、{"detail":"未知端点 xxx/yyy"}、{"detail":"Not Found"}
422 参数校验失败（FastAPI 风格）：缺 source/endpoint、params 不是对象、fields 不是字符串数组、limit 不在 1–500、timeout_ms 不在 50–500、它们不是整数 {"detail":[{"type":...,"loc":[...],"msg":...,"input":...}]}
500 网关内部错误（信封编码失败） {"detail":"网关内部错误"}
503 /readyz 在注册表为空时 {"ok":false,"sources":0,"offline":false}

错误响应体里没有 meta：4xx/5xx 是请求层失败， 降级是业务层降级，两者要分开处理。

错误类型（meta.errors[].type）

查询接口即使返回 200，失败信息也在信封的 meta.errors 数组里。 每项形如 {"type":"timeout","message":"上游超过 400ms 预算, 已降级"}； 带上游状态码时多一个 status 字段。

type含义典型处置
timeout上游超过 400ms 预算（或解析用完了剩余预算），已降级稍后重试，命中缓存；或用 fallback.upstream_url 直连
budget_exceeded客户端可见耗时超过本次预算结果被截到前 5 条且 truncated=true，按需重试
upstream_error上游返回了 ≥400 的状态码（带 status）看 meta.upstream.status，多半是参数问题
parse_error上游返回了但解析不了（结构与端点定义对不上）核对端点定义，或直连上游
response_too_large响应体超过上限被截断，或端点是文件型大响应减小 limit 重试，或直连上游
missing_param缺端点要求的必填参数照端点定义补 params
endpoint_not_found该源没有这个端点 id用描述接口查端点清单
not_found源 id 解析不出来用 /v1/sources 查真实 id
bad_template端点的 URL 模板不可用这是数据问题，请报 issue
contact_required该源要求 User-Agent 带联系邮箱，但没配 A_GATEWAY_CONTACT设置环境变量后重启
offline网关处于离线模式，只给元数据与缓存关掉 A_GATEWAY_OFFLINE
stale缓存已过期，返回陈旧值并在后台刷新可接受，或稍后再调一次拿新值
internal_error网关内部错误（panic 已被兜住）带 trace id 查日志
i还有三个传输层错误名

DNS 解析失败、连接被拒、连接被重置这类传输层故障， type 用的是 httpx 异常类名：ConnectError、ReadError、 UpstreamError（Python 参照实现用 type(e).__name__，Go 网关映射到同样的名字）。 处理方式和 timeout 一样：看 fallback，稍后重试。

端点参数与响应结构

GET /v1/sources/{id}/endpoints/{eid} 的 data.endpoint 有这些字段：

字段类型说明
id / namestring端点 id 与端点名
methodstring对上游的 HTTP 方法，通常 GET
url_templatestring带 {param} 占位的上游 URL
params[]array请求参数表：name、in（query/path/header/body）、type、required、desc、pattern、default、example
headersobject端点专有请求头（如 Accept）
page_sizeint / null上游页大小；没定义就是 null，此时用默认页大小 25
response.media_typestring上游响应类型，如 application/json
response.shapestringobject / array / csv / tsv / xml / jsonl / text
response.fields[]array上游响应里的字段：name、type、desc、path（在上游响应中的位置）
response.item_pathstring列表数据在上游响应里的路径（如 data）
response.item_shapestringlist（数组）或 map（字典值域）
response.total_fieldstring总数字段的路径（如 meta.pagination.total）
response.notesstring坑位说明
cache_ttl_sint该端点的缓存 TTL（秒）；没定义时默认 900
budget_msint端点声明的上游预算；默认 400，但放大不了客户端侧的 500ms 硬上限
notesstring端点级备注

item_path + item_shape + total_field 这三样决定了网关 怎么从上游响应里挖出列表、怎么算 meta.total——它们由源定义维护， 你只管按端点定义传参。

通用端点 entry

有些源在 data/endpoints.json 里没有专门的端点定义。网关会给它自动派生一个 id 为 entry、名字是「官方入口(通用)」的通用透传端点， 直接取该源的官方入口 URL：

console
$ curl -s http://127.0.0.1:8848/v1/sources/sec_iapd_form_adv/endpoints/entry
{
  "meta": {
    "source": "sec_iapd_form_adv",
    "endpoint": "entry",
    "schema_version": "1.1"
  },
  "data": {
    "source": {
      "id": "sec_iapd_form_adv",
      "name": "SEC IAPD / Form ADV",
      "...": "源元数据子集"
    },
    "endpoint": {
      "id": "entry",
      "name": "官方入口(通用)",
      "method": "GET",
      "url_template": "https://adviserinfo.sec.gov",
      "params": [],
      "headers": {},
      "page_size": null,
      "response": {
        "media_type": "*/*",
        "shape": "object",
        "fields": [],
        "notes": "通用透传端点(官方入口直取);结构随官方文件而定, 建议先取该源的专用端点"
      },
      "cache_ttl_s": 900,
      "budget_ms": 400,
      "notes": ""
    }
  }
}

几个要注意的点：

  • 它的 shape 按官方入口的后缀猜：.xml → xml，.csv → csv，.tsv → tsv，其余按 object 处理；media_type 同理，默认 */*。
  • 它没有字段定义（fields 为空），所以你拿不到字段投影，也拿不到 total。
  • 官方入口常常是整份大文件，limit 帮不上忙——这类响应会被判成"文件型大响应"并降级，提示你直连上游。
  • 优先用该源的专用端点；只有在没有专用端点时才用 entry。
