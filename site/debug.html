API 调试台

这一页既是能真发请求的在线控制台,也是命令行调试手册。 控制台直接向网关发 POST /v1/query、读统一信封、生成等价 curl; 下面的命令行段落则是同一套动作的终端版本,适合贴进 issue、PR 描述或 CI。

调试台怎么用

三行起服务,然后打开本页:

bash
make up                            # 起网关(127.0.0.1:8848);或 make gateway-run 跑本地二进制
python3 scripts/serve_docs.py        # 起文档站(127.0.0.1:8000),并把 /__gateway/* 同源代理到网关
# 浏览器打开 http://127.0.0.1:8000/debug.html

scripts/serve_docs.py 不是普通的静态服务器:它把 /__gateway/<path> 原样转发到 http://127.0.0.1:8848/<path>(method/body/query 不变, 转发 Content-Type、Accept、X-Gateway-Trace-Id、 X-Request-Id、User-Agent)。 所以调试台默认走 /__gateway 前缀 —— 同源,不触发浏览器跨域。

✓前缀填什么,决定你能不能拿到响应
  • 同源代理(默认,推荐):前缀填 /__gateway。 网关没起时,代理会返回 502 和一段 JSON,里面 detail 说明"网关不可达", hint 说明"先启动网关(make up 或 make gateway-run), 再刷新本页"。调试台会原样显示这两段。
  • 直连:前缀改成完整 URL(如 http://127.0.0.1:8848)。 网关没有开 CORS 响应头,所以浏览器会拦截跨域响应 —— 只有当这个文档站页面本身就与网关同源(例如你也用同一个地址起了网关)才可用。 调试台会明确区分"跨域被拦截"和"网关连不上",不会假装成功。

网关给上游取数留的墙钟预算是 400ms(留 100ms 给解析与序列化)。 从中国直连欧美上游,实测往返常常 0.4–7.5s —— 所以跨境源第一次调用大概率 degraded=true,meta.errors[0].type == "timeout", 同时 meta.fallback.upstream_url 给出可直连的上游地址。

网关会在后台补数。等几秒再点一次同一个查询,就命中缓存: cached=true、latency_ms 常是 1ms。调试台在检测到降级时会给「重试」按钮, 点它会在约 1.5 秒后自动重发同一个请求。

命令行调试

控制台的每个动作在终端里都有一条对应命令。下面这几条按"排查顺序"排列。

curl 速查

bash
# 1) 活着吗? /livez = 进程活着, /readyz = 注册表已加载能接流量, /healthz = 健康探针
curl -s http://127.0.0.1:8848/livez | python3 -m json.tool
curl -s http://127.0.0.1:8848/readyz | python3 -m json.tool

# 2) 列源(关键词过滤)
curl -s "http://127.0.0.1:8848/v1/sources?q=制裁" | python3 -m json.tool

# 3) 看端点怎么调 —— 先看它,别试错
curl -s http://127.0.0.1:8848/v1/sources/crossref/endpoints/works | python3 -m json.tool

# 4) 查一次
curl -s -X POST http://127.0.0.1:8848/v1/query -H 'Content-Type: application/json' \
  -d '{"source":"crossref","endpoint":"works","params":{},"limit":3}' | python3 -m json.tool

证据关卡:verify_source.py

这是加源流程的硬门槛,也是判断"我声明的字段到底对不对"的唯一可靠办法: 它真的去请求上游,然后断言声明的元数据。

bash
python3 scripts/verify_source.py "My Journal API" --direct-only

断言这四件事:

  • 声明的 response.item_path 在真实响应里确实指向一个列表;
  • 声明的 response.total_field 确实是一个数字;
  • response.fields 里声明的字段名在返回条目里确实出现;
  • 本次调用没有降级(降级的调用不算"验证通过")。
退出码含义你该做什么
0已用真实数据验证通过进入下一步
1断言失败,或本次调用是降级的先看断言名,见下表
2根本连不上上游环境问题,不是源的问题 —— 如实报告,不要伪造
失败的断言名说明处置
not_degraded这次调用降级了(通常是超时)网络/预算问题,别改元数据
item_path_resolves_to_list声明的 item_path 没指向列表元数据写错了,去改 data/endpoints.json
total_field_resolves_to_number声明的 total_field 不是数字元数据写错了,去改
required_params_available必填参数既没有 example 也没有 default给参数补 example,或用 --params 补上
declared_fields_present声明的字段名在真实响应里找不到(严重度 warn)核对字段路径写法
!为什么建议要加 --direct-only

走网关时上游预算只有 400ms,而从中国到欧美上游的实测往返常常是 0.4–7.5s —— 于是调用会正常地降级, not_degraded 断言随之失败、退出码变成 1。 那不是元数据写错了,是网络慢。 --direct-only 让验证脚本直连上游(带自己的超时),不受网关 400ms 预算影响, 才能真正回答"我声明的字段对不对"。

代价是直连验证不覆盖网关这一段,所以两条都要跑:

bash
python3 scripts/verify_source.py "My Journal API" --direct-only   # 元数据对不对
python3 scripts/verify_source.py "My Journal API"                  # 网关在预算内能不能通

第二条在网络慢时返回 DEGRADED + 退出码 1,这是预期行为, 不是源有问题;它证明的是"网关在预算内优雅降级并给出直连兜底"。

交付物:demo.py

产出三样东西:端点说明(干什么的、必填参数、限速口径)、一条可复制的 curl、真实的响应信封(data 截断到前 1–2 条)。

bash
python3 scripts/demo.py "My Journal API" --limit 2

注意:demo.py 遇到降级会非零退出 —— 它不拿降级数据当"跑通了"给人看。

复验全部源(逐源子进程,单源失败不拖垮整批;退出码 = 未通过源数,上限 100):

bash
python3 scripts/verify_source.py --all --json --timeout 15

指标与日志

bash
curl -s http://127.0.0.1:8848/metrics | grep asg_     # Prometheus 指标
curl -s http://127.0.0.1:8848/v1/stats | python3 -m json.tool
curl -s http://127.0.0.1:8848/openapi.json | head -40             # OpenAPI 3.1 描述

docker compose logs -f gateway     # 容器部署的日志
journalctl -u a-source-gateway -f  # systemd 部署的日志

GET /v1/stats 里三个块值得盯:

  • cache —— 命中率(hit_rate)、条目数、缓存字节数。命中率低先看是不是每次都在打新查询键。
  • prewarm.states —— 每个预热源是 ok 还是 degraded。一堆 degraded 通常是上游慢,不是源写错了。
  • parser —— 当前解析引擎是 python 还是 go。

trace id

响应头带 X-Gateway-Trace-Id,信封 meta.trace_id 里也有同一个值。 入站时带 X-Gateway-Trace-Id 或 X-Request-Id 会被复用 —— 所以客户端自己生成的 request id 可以贯穿网关与日志:

bash
curl -s -D - -o /dev/null -X POST http://127.0.0.1:8848/v1/query \
  -H 'Content-Type: application/json' -H 'X-Request-Id: my-trace-001' \
  -d '{"source":"gleif_lei","endpoint":"lei_records","params":{"size":1},"limit":1}' | grep -i trace

故障定位表

按症状查。先看 meta.errors[] 和 meta.fallback —— 它们会直接告诉你原因和下一步。

症状先查什么处置
degraded=true meta.errors[0].type、meta.upstream.status 跨境源首次调用大概率如此:等几秒再调一次命中缓存;或用 meta.fallback.upstream_url 直连上游
timeout meta.upstream.latency_ms 与端点 budget_ms 上游慢于 400ms 预算。调小 page_size,或改用 --direct-only 验证元数据
budget_exceeded 该端点的 budget_ms 与上游实际延迟 同上;必要时调小 page_size
missing_param 错误消息里的参数名 在参数区补上该必填参数(端点声明的 example 会自动填,但可能已被清空)
endpoint_not_found 端点 id 拼写 先 GET /v1/sources/{id} 看端点列表;注意没有专用端点的源只有 entry
contact_required(403) 上游是否要求 UA 带邮箱 设 A_GATEWAY_CONTACT=you@example.com 后重启网关再试
response_too_large 端点 page_size 与 limit 调小 page_size 或 limit;文件型源应直连上游
offline GET /readyz 与 /v1/stats 的 offline 网关处于离线模式,数据不是实时的 —— 查上游可达性后再重试
stale meta.cache_age_s 命中的是过期缓存(上游已失败),看 meta.errors[] 的真实原因
parse_error 端点 response.shape 与 item_path 上游返回结构与声明不一致 —— 回步骤 6 改元数据,别改解析器
upstream_error meta.upstream.status 上游返回了错误码(4xx/5xx)。先看是不是 403 要邮箱,再看是不是上游自身故障
HTTP 502 + detail / hint 这是文档站代理返回的,不是网关 网关没起或地址不对:按 hint 起网关(make up / make gateway-run),或改前缀
浏览器控制台报跨域被拦截 前缀是不是完整 URL、且与本页不同源 网关没开 CORS 头。改回 /__gateway 同源代理,或让文档站与网关同源
