信封与降级

网关的每个查询都返回同一个信封：{meta, data, fields}。 meta 说清楚"这次请求打到哪、用了多久、有没有降级、命中多少"， data 只放结果本身，fields 说明你点名了哪些字段。 机器读 meta，业务只读 data——两者严格分离， 所以降级不会把你的解析逻辑搞崩。

信封三段式

json
{
  "meta": {
    "request_id": "",
    "trace_id": "a89c0fbebbae1b64e5dfa8d30e261d6a",
    "schema_version": "1.1",
    "source": "gleif_lei",
    "endpoint": "lei_records",
    "parser": "python",
    "upstream": {
      "url": "https://api.gleif.org/api/v1/lei-records?page%5Bsize%5D=25&page%5Bnumber%5D=1",
      "method": "GET",
      "status": null,
      "latency_ms": 402
    },
    "latency_ms": 402,
    "budget_ms": 500,
    "cached": false,
    "cache_age_s": 0,
    "degraded": true,
    "offline": false,
    "count": 0,
    "total": null,
    "truncated": false,
    "next_cursor": null,
    "rate_limit": {},
    "fallback": {
      "upstream_url": "https://api.gleif.org/api/v1/lei-records?page%5Bsize%5D=25&page%5Bnumber%5D=1",
      "method": "GET",
      "hint": "网关预算内取不到;可直连上游, 或稍后重试(后台正在补数)"
    },
    "errors": [
      { "type": "timeout", "message": "上游超过 400ms 预算, 已降级" }
    ]
  },
  "data": [],
  "fields": []
}
段内容谁该看
meta20 个字段的请求元信息：打向哪个源、用了多少预算、有没有降级、命中没命中缓存你的框架/SDK：决定要不要重试、要不要走兜底
data结果本身：通常是列表，也可能是单个对象（shape=object 的端点）你的业务代码
fields本次点名的字段名数组你的类型校验/文档生成
i哪些接口返回信封

GET/POST /v1/query 与 GET /v1/sources 返回完整三段式。 GET /v1/sources/{id} 与 GET /v1/sources/{id}/endpoints/{eid} 只返回 {meta, data}（没有 fields）； /、/v1/stats、三个探针、/v1/schema 各自有自己的形状，不走信封。

meta 字段全表

字段类型含义什么时候非空
request_idstring本次请求 idGo 网关目前恒为空字符串（Python 参照实现会生成 12 位 hex）。做关联请用 trace_id
trace_idstring贯穿网关日志、上游调用与解析 worker 的关联 id总是有：入站带 X-Gateway-Trace-Id / X-Request-Id 就复用，否则随机生成 32 位 hex
schema_versionstring信封结构版本总是有，恒为 "1.1"
sourcestring实际命中的源 id总是有。传入别名时这里给的是解析后的规范 id
endpointstring端点 id总是有
parserstring真正解析出数据的引擎总是有："python" 或 "go"
upstreamobject上游那一次调用的详情（4 个子字段，见下）总是有对象；URL 在还没渲染时就可能是空串
latency_msint客户端可见总耗时（毫秒）总是有。做过任何工作的请求至少是 1，不会报 0
budget_msint本次生效的总预算总是有。默认 500；把 timeout_ms 调小，它会跟着变小
cachedbool本次结果来自缓存命中新鲜缓存、或命中过期但可用的缓存时为 true
cache_age_sint缓存年龄（秒）命中缓存时是缓存已存放的秒数；未命中是 0
degradedbool这次返回不是完整正常结果超时、解析失败、上游报错、响应过大、缓存陈旧、缺联系邮箱等任何降级路径下为 true
offlinebool网关处于离线模式只有 A_GATEWAY_OFFLINE 打开时为 true，此时只给元数据与缓存
countint本次返回的条数总是有。列表就是长度，单个对象算 1，空结果是 0
totalint / null上游的记录总数来自端点定义的 total_field；上游没给这个字段时，列表结果退化成"本次条数"；降级兜底数据通常是 null
truncatedbool结果被截断了超过 limit、或上游总数大于返回条数、或超预算被砍到前 5 条时为 true
next_cursorstring / null下一页游标保留字段，Go 网关目前恒为 null；翻页请用端点自己的 page / offset 参数
rate_limitobject限速余量保留字段，Go 网关目前恒为 {}；限速口径请读源元数据的 limits
fallbackobject降级时的直连兜底信息降级时非空，含 upstream_url、method、hint；正常时是空对象 {}
errorsarray本次调用的错误列表正常时是空数组 []；降级时至少有一项，形状是 {"type":...,"message":...}，带上游状态码时多一个 status

upstream 的四个子字段

字段类型含义
urlstring实际请求的上游 URL（模板渲染 + 参数归一 + percent 编码之后的结果）
methodstring对上游的 HTTP 方法，通常是 GET
statusint / null上游状态码。为 null 表示压根没拿到响应（超时、连不上）；有值表示拿到了（哪怕是 4xx/5xx）
latency_msint上游那一次调用耗时（不含解析与序列化）

data 与 fields

data 是上游结果经解析、投影、截断之后的产物。它通常是数组，但端点定义的 response.shape 是 object 且没有 item_path 时， data 会是一个对象——按 shape 处理，不要默认它一定是 list。

fields 是你请求里点名的字段（fields 参数），没点名时是空数组 []。它不是"实际返回了哪些字段"的清单——要那个信息，请看端点定义里的 response.fields[]（见 API 参考）。

console
$ curl -s -X POST http://127.0.0.1:8848/v1/query \
    -H 'Content-Type: application/json' \
    -d '{"source":"gleif_lei","endpoint":"lei_records","params":{"size":2},"fields":["type","id"],"limit":2}'
{
  "meta": {
    "...": "...",
    "count": 2,
    "total": 3471073,
    "truncated": true
  },
  "data": [
    { "type": "lei-records", "id": "335800YDCVLAQSJR5968" },
    { "type": "lei-records", "id": "335800B0F6URAV052H87" }
  ],
  "fields": ["type", "id"]
}
  • 投影按顶层 key 匹配：点名 type 和 id，每条记录就只剩这两个顶层字段；嵌套结构不会被拆开。
  • 投影在解析之后做，不改变上游请求——带不带 fields 命中的是同一个缓存条目。
  • 截断规则：limit 砍掉超出部分并置 truncated=true；上游总数大于返回条数时同样置 truncated=true。

降级语义

!降级是 200，不是 5xx

网关取不到数据时不会返回错误码，而是返回 200 + meta.degraded=true + meta.errors[] + meta.fallback。 只看 HTTP 状态码的代码会漏掉降级——务必检查 meta.degraded。

什么时候会降级

场景表现
上游慢于预算timeout + fallback.upstream_url，后台同时补数
上游返回了但解析不了parse_error，提示直连上游
上游返回 ≥400upstream_error（带 status），data 仍可能是空
响应体过大 / 端点是文件型大响应response_too_large，提示减小 limit 或直连
端点要联系邮箱但没配 A_GATEWAY_CONTACTcontact_required，给出配置提示
缓存已过期stale：先给你陈旧值，后台刷新（这是 SWR，不是故障）
网关离线offline：只给元数据与缓存
客户端可见耗时超预算budget_exceeded：结果被砍到前 5 条并置 truncated=true

下面是从 gleif_lei / lei_records 真实抓到的降级返回： 上游 GLEIF 在 400ms 预算内没回话，网关给了兜底。

      "method": "GET",
      "hint": "网关预算内取不到;可直连上游, 或稍后重试(后台正在补数)"
    },
    "errors": [

    ]
  },

}

逐条读这个信封：

  • upstream.status = null —— 压根没拿到上游响应，不是上游报错。
  • upstream.latency_ms = 402 —— 它一直等到 402ms 才放弃，正好卡在 400ms 预算上。
  • data = [] 且 count = 0 —— 没有数据可给。
  • fallback.upstream_url —— 你可以直接拿这个 URL 去上游取；hint 告诉你还有第二个选择：稍后重试。
  • errors[0].type = "timeout" —— 机器可判定的失败原因。
✓等几秒再调一次

降级的同时网关会在后台补数。再调一次同一个查询，就直接命中缓存：

json
"cached": true,
"latency_ms": 1,
"cache_age_s": 17,
"degraded": false,
"count": 2,
"total": 3471073

遇到降级怎么办

  1. 先重试一次

    同一个查询在几秒后再调，通常就命中后台补好的缓存（cached=true、latency_ms 常是 1ms）。这是最省事的路径。

  2. 或者直连上游

    拿 meta.fallback.upstream_url 和 meta.fallback.method 直接请求上游。注意官方限速是授权条件，请遵守各源的限速口径。

  3. 或者减小问题规模

    减小 limit、减少 params，能降低解析耗时，也更容易挤进预算。响应过大时的提示就是这个意思。

缓存语义

项行为
位置进程内内存缓存，不落盘、不跨副本共享；网关重启就是冷缓存
风格SWR（stale-while-revalidate）：过期条目仍然可读，同时后台刷新
TTL取端点定义的 cache_ttl_s；端点没定义时默认 900 秒
热条目同一个键被命中 3 次以上，TTL 缩短到 TTL/4（最低 30 秒），让热数据更新更快
缓存键source | endpoint | 上游 URL | params；email 不进键，页大小参数归一成一个有效值
不进键的limit 与 fields —— 它们是网关在解析后做的截断与投影，不影响上游响应
容量默认 512 条 / 32MB，超了按 LRU 淘汰；单条大于上限的干脆不缓存
新鲜命中cached=true、cache_age_s 是缓存年龄，degraded=false
过期命中cached=true、degraded=true、errors[].type="stale"，同时后台刷新
只缓存成功的响应上游状态码 ≥400 的响应不进缓存
观测GET /v1/stats 的 cache 段：entries、bytes、hits、misses、stale_hits、hit_rate

缓存键不含 limit 是个好消息：limit=2 和 limit=50 打的是同一个上游请求，只是网关在返回前切得不一样。

预算与延迟

预算值留给谁
客户端可见总预算500ms上游 + 解析 + 投影 + 序列化，全部加起来
上游取数墙钟预算400ms只给上游那一次 HTTP 调用
保留100ms解析 / 投影 / 序列化 / 框架开销
  • 实际给上游的超时 = min(端点 budget_ms, 剩余预算)，最低 50ms。 端点自己写 budget_ms: 5000 也放大不了 500ms 这个硬上限—— 那是后台补数用的预算，不是客户端侧的。
  • timeout_ms 会被钳在 ≤500。把它调小（最小 50）是让网关更早放弃、 更早降级；调大无效。
  • 客户端可见耗时超过预算时：加一条 budget_exceeded 错误、 置 degraded=true，并把 data 列表截到前 5 条、 置 truncated=true。
  • 响应头 X-Gateway-Latency-Ms 就是这个客户端可见耗时，和 meta.latency_ms 一致。

错误类型全表

错误都在 meta.errors[] 里，每一项形如 {"type":"timeout","message":"上游超过 400ms 预算, 已降级"}； 带上游状态码时多一个 status 字段： {"type":"upstream_error","status":503,"message":"..."}。

type触发条件HTTP 码典型 message
timeout上游超过 400ms 预算，或解析用完了剩余预算200上游超过 400ms 预算, 已降级
budget_exceeded客户端可见耗时超过本次预算200客户端可见耗时 520ms 超过预算 500ms
upstream_error上游返回 ≥400 的状态码（带 status）200上游响应体前 300 字符
parse_error上游返回了，但按端点定义解析不出来200解析器报错信息（截到 300 字符）
response_too_large响应体超过上限被截断，或端点是文件型大响应200响应超过 1MB 上限被截断;请减小 limit 或直连上游
missing_param缺端点要求的必填参数200缺少必填参数 cik
endpoint_not_found该源没有这个端点 id200gleif_lei 没有端点 xxx
not_found源 id 解析不出来200未知数据源 xxx
bad_template端点的 URL 模板不可用（数据问题）200模板错误信息
contact_required该源要求 UA 带联系邮箱，但没配 A_GATEWAY_CONTACT200xxx 要求 User-Agent 里带联系邮箱, 当前未配置(A_GATEWAY_CONTACT)
offline网关处于离线模式200网关处于离线模式, 仅提供元数据与缓存
stale缓存已过期，返回陈旧值并在后台刷新200缓存已过期 1200s, 返回陈旧值并在后台刷新
internal_error网关内部错误（panic 已被中间件兜住）200网关内部错误: ...
ConnectErrorDNS 解析失败 / 连接被拒 / TLS 证书问题200传输层错误信息
ReadError连接被重置 / 读取中断200传输层错误信息
UpstreamError其它传输层故障200传输层错误信息

最后三个是传输层的名字（Python 参照实现用 type(e).__name__， Go 网关映射到同样的名字）。它们的处置和 timeout 一样：看 fallback，稍后重试。

i请求层错误不在信封里

400 / 422 / 404 / 500 这些是 请求层失败，响应体只有 {"detail": ...}，没有 meta。 处理顺序：先判 HTTP 状态码，再判 meta.degraded，最后才读 data。

trace id 与排查

网关给每个请求一个 trace_id，它同时出现在响应体 （meta.trace_id）、响应头（X-Gateway-Trace-Id）和 网关日志里。

方向头行为
入站X-Gateway-Trace-Id 或 X-Request-Id带了非空值就复用成这次的 trace id，你的日志和网关日志就能对上一条
入站都没带随机生成一个 32 位 hex
出站X-Gateway-Trace-Id回显本次 trace id（查询接口与 4xx 错误都有）
出站X-Gateway-Latency-Ms客户端可见耗时（毫秒）
bash
# 带上自己的 trace id，出问题时拿它去查网关日志
curl -s -D - -X POST http://127.0.0.1:8848/v1/query \
  -H 'Content-Type: application/json' \
  -H 'X-Gateway-Trace-Id: my-trace-20261024-001' \
  -d '{"source":"gleif_lei","endpoint":"lei_records","params":{"size":2},"limit":2}'

排查顺序：

  1. 先看 HTTP 状态码

    非 200 → 请求层问题，看 detail：422 是参数写错了，404 是源或端点 id 不存在，400 是 GET 的 params 不是合法 JSON。

  2. 再看 meta.degraded

    200 + degraded=true → 业务层降级，看 meta.errors[].type 判断原因，看 meta.fallback 决定重试还是直连。

  3. 最后看耗时

    meta.latency_ms 接近 meta.budget_ms 说明卡在预算上；meta.upstream.latency_ms 大而 meta.latency_ms 也大，说明时间花在上游；上游快但总耗时长，说明时间花在解析。

  4. 拿 trace id 去查日志

    meta.trace_id（或你传进去的那个）就是网关日志里的关联键。

i422 不带 trace 响应头

参数校验失败（422）的响应只写 {"detail":[...]}，不带 X-Gateway-Trace-Id 响应头；它是你自己请求写错了，日志里也未必有记录， 改参数就行。

接入建议

把"HTTP 层错误"和"业务层降级"分成两层处理，就不会被降级打懵：

python
import uuid
import requests

GATEWAY = "http://127.0.0.1:8848"


def query(source, endpoint, params=None, fields=None, limit=20, timeout_ms=500):
    trace_id = uuid.uuid4().hex
    resp = requests.post(
        f"{GATEWAY}/v1/query",
        json={
            "source": source,
            "endpoint": endpoint,
            "params": params or {},
            "fields": fields or [],
            "limit": limit,
            "timeout_ms": timeout_ms,
        },
        headers={"X-Gateway-Trace-Id": trace_id},
        timeout=timeout_ms / 1000 + 0.5,
    )

    # 第一层: 请求层错误(4xx/5xx)—— 参数写错、源不存在
    resp.raise_for_status()

    env = resp.json()
    meta = env["meta"]

    # 第二层: 业务层降级 —— 200 但数据不完整
    if meta["degraded"]:
        reason = meta["errors"][0]["type"] if meta["errors"] else "unknown"
        # fallback 里给你了直连上游的 URL 和提示
        print(f"[degraded:{reason}] trace={meta['trace_id']} fallback={meta['fallback']}")

    # 第三层: 结果本身
    return env["data"], meta
bash
# shell 里最简的判断:只看 degraded 字段
curl -s -X POST http://127.0.0.1:8848/v1/query \
  -H 'Content-Type: application/json' \
  -d '{"source":"gleif_lei","endpoint":"lei_records","params":{"size":2},"limit":2}' \
  | python3 -c 'import json,sys; e=json.load(sys.stdin); m=e["meta"]; print("degraded" if m["degraded"] else "ok", m["cached"], m["count"], m["trace_id"])'
  • 给每个请求带自己的 trace id：出问题时能直接在自己的日志和网关日志之间对上。
  • 先读 meta 再读 data：不要假设 data 非空。
  • 降级时优先重试，别急着自己直连上游——直连要遵守官方限速口径。
  • 缓存是进程内的：不要假设另一个副本能命中你这边热过的条目。
  • 大批量取数走批量文件，不要靠调接口硬凑——限速与预算都是授权条件。
